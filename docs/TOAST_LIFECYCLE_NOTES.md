# 导入提示输入与计时回归

## 问题与证据

`dd916cf555d69cf9d85dea50b4269aa0f63dc529` 的 CI 在最后一套提示输入测试失败。前两条路线的确认点击确实命中按钮，提示当时可见；第三条 200% 字号路线在等待提示时失败。不能把它简单写成新提示自然显示满 3500ms：第二条确认发生于约 4053.2ms，之后第三次导入及可见性检查已通过，但约 4992ms 的第三条 AVG 输入时提示已经消失。新提示最多存活约 938.8ms。

独立真实文件导入复现：两次通知相隔约 2123ms，第二条只存活约 1409.6ms 就被第一条的旧 timeout 删除。另给旧测试增加 4500ms 的主机延迟，也会因提示正常过期而失败；这是测试依赖主机速度的独立问题，不冒充原 CI 的根因。

运行时最小修复只给当前提示保存 timeout 句柄，替换提示时取消旧句柄，到期清空句柄。每条最新提示仍使用原本的 3500ms。内容、role、样式、可见性、指针策略以及游戏规则不变。

## 三类验证，结论分开

1. **受控时间的可见提示输入。** Playwright 在页面加载前安装时钟，启动完成后、第一次导入前暂停。仍由实际文件输入创建通知，使用原 DOM、CSS、真实鼠标事件及 Tab+Enter。共享页面依次跑直接导入、非法后合法导入、200% 键盘、4500ms 主机延迟鼠标、4500ms 主机延迟 200% 键盘。不是声称真实时间中通知会超时不消失。
   - 所有捕获的指针和键盘事件必须为可信事件，发生时同一内容的 status 可见；AVG、选择、确认、锁定、提交、跳转均核对实际目标且恰好激活一次。
   - 每次原始状态、预览、确认、锁定草稿、一次性支付、历史以及第20年整个世界继续与独立模拟结果逐字比较。锁定点击之前每个事件还核对世界未变。
   - 主机延迟由 Node 定时器产生，超过 3500ms；报告同时记录主机实耗和应用时钟零推进。没有强制点击、重复补点、隐藏提示、注入 CSS 或重建提示。
2. **受控时间的生产 timeout 边界。** 使用真实注册的计时器回调推进应用时钟，单条通知在 3499ms 仍可见、3500ms 消失。合法→合法与非法→合法分别间隔 1800ms，再跨过第一条旧截止点；新通知必须继续可见，并在自己的 3499/3500ms 边界消失。原源码在“合法→合法跨旧截止点”明确红测，不能靠隔离页面把问题藏掉。
3. **未 mock 的浏览器时间。** 新页面不安装时钟、不包装 timer。MutationObserver 在浏览器内记录实际出现和消失，避免工具往返太慢而漏看短暂通知。单条导入自然显示约 3500ms 后消失，延迟后的真实 Tab+Enter 仍能进入确认且不改世界。另测合法→合法及非法→合法重叠：第一条实际出现后，用浏览器原生 timer 在 1800ms 后创建 File/DataTransfer 并触发已有导入处理器。此操作明确是生命周期驱动，不作为真实鼠标手势证据；不直接赋值世界或提示。第二条必须在第一条仍可见时开始，不能被旧截止点清掉，且自然存活约 3500ms。

原生 timer 在繁忙环境中可能晚执行，因此真实时间只限制不得提前结束，并保留最终消失的等待上限；精确 3499/3500ms 合同由受控时间边界另行验证。测试以原始事件及观察记录保留证据，不通过放宽目标、状态或成本断言来修正时序。
